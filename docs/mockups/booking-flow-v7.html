Route-inferred booking flow (v7)

The passenger chooses a Pickup and a Destination. Where the airport appears decides the journey — nobody is asked whether they are arriving or departing, and there is no preset screen. The flight finder is a contextual tool that appears only for arrivals, and what it produces is a recommendation: the flight service says when the aircraft lands, LinkMia decides the operational buffer.

The route answers the question

  • No preset screen, no direction tabs. Put MIA in Pickup and it is an arrival; put it in Destination and it is a departure. The passenger is never asked.
  • Airports are recognised by identity, not by string. AIRPORTS is a map of verified codes and an endpoint is an airport only when kind === 'airport' and its code is in that map. Nothing searches an address for the word “airport”.
  • Exactly one airport, for now. The availability line sits under the fields before anyone is refused, and a refusal keeps everything the passenger typed — it explains, it never undoes.
  • The browser still speaks today’s contract: airport in Pickup → pickup, airport in Destination → dropoff.
  • What Route Intent v2 actually costs. The passenger screen stays the same; the server contract, the signed token, the database route identity, the pricing rules and the tests all expand behind it. This mockup only shows that the interface would not need redesigning — it is not a claim that one function changes.

The flight finder is a tool, not a step

  • It appears only for arrivals and opens itself once the route is complete — not over a half-filled form. Choose a pickup time instead sits outside the scrolling area, so the escape is on screen the moment the sheet opens, and closing the sheet never disturbs the route.
  • Flight number when they know it; Route (flying from + the arrival date already on screen) when they don’t; Choose a pickup time instead when the lookup is no use.
  • Domestic or international is never asked. It is derived from the flight’s origin — and San Juan is treated as a domestic arrival, because there is no immigration queue.
  • “Recommended” is the load-bearing word. The flight tells us when the aircraft lands; LinkMia owns the buffer, and the passenger can always override it.
  • Departures get an optional flight number only. A derived departure time needs drive time, lead time, traffic and an operational buffer — that is a later release, and the copy promises nothing.

Still unresolved, and visible in the code

  • The buffer numbers are placeholders. BUFFER is one named constant with 30/45 minutes and a comment saying so. The plan in the repo says 35–40 plus 30 for customs in its body and 45 in its decision table; that contradiction is a dispatch decision, not a design one.
  • Live status is displayed but not acted on. A delayed flight shows its delay; nothing reschedules a committed driver yet, and no copy claims otherwise.
  • Route lookup needs a schedules feed, which costs more than a flight-number call. Shipping the flight-number tab first leaves the Route tab as a later upgrade to the same sheet.
  • Ports and general point-to-point stay refused until Route Intent v2. That release expands the server contract, the signed token, the stored route identity, the pricing rules and the tests — the passenger screen is the one part that would not need redesigning.
  • None of this belongs in the production plan yet. Pricing stabilisation and Manage Ride come first; this is a reference for the interface those releases eventually sit behind.
